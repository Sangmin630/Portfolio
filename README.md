## 프로젝트 개요

GameOps는 게임 고객 문의를 자동 분류하고, FAQ·정책 문서·운영 DB를 기반으로 답변을 생성하는 AI 고객센터 운영 시스템입니다.

게임 유저가 챗봇에 문의를 입력하면 문의 유형에 따라 FAQ, 결제/환불, 버그/오류, VOC 흐름으로 분기되고, 각 에이전트가 필요한 문서 검색 또는 DB 조회를 수행한 뒤 근거 기반 답변을 제공합니다.

또한 CS 자동화와 Weekly Report 기능을 통해 외부 커뮤니티 문의 분석, 답변 초안 생성, 운영 인사이트 리포트까지 지원하는 구조로 설계했습니다.

## 주요 기능

* 카테고리 기반 챗봇 문의 분기
* FAQ / 공지 / 정책 문서 기반 RAG 답변 생성
* 결제, 환불, 아이템 지급, 가챠 로그 기반 DB 조회 답변
* 버그 및 오류 문의 접수
* VOC 및 개선 요청 접수
* 문의 답변 초안 및 최종 응답 저장
* Redis 기반 FAQ/RAG 검색 캐시
* CS 자동화 답변 초안 생성
* Weekly Report 기반 운영 인사이트 생성

## 시스템 구성

GameOps는 크게 세 가지 시스템으로 구성됩니다.

* Chatbot: 사용자가 직접 문의를 입력하고 AI 답변을 받는 고객지원 챗봇
* CS Automation: 외부 커뮤니티 문의를 분석하고 답변 초안 또는 운영자 검토 대상으로 분류하는 자동화 시스템
* Weekly Report: 문의 현황, 주요 이슈, 반복 요청을 집계하여 운영 리포트를 생성하는 보고 시스템

## 담당 역할

### 챗봇 백엔드

챗봇 백엔드 영역에서는 프론트엔드에서 전달된 사용자 문의가 FastAPI API를 거쳐 LangGraph 기반 워크플로우로 실행되고, 최종 응답으로 반환되는 흐름을 구현 및 개선했습니다.

* 사용자 문의 접수 → 카테고리 분기 → 에이전트 실행 → 답변 생성 → 최종 응답 반환 흐름 개발
* 문의 내용을 `qa_ticket`에 저장하고, 답변 초안 및 최종 응답이 DB에 저장되는 백엔드 흐름 연동
* 답변 생성 이후 문의 상태가 `pending`으로 남거나 최종 응답이 저장되지 않는 문제를 분석하고 저장 로직 개선
* 문의 내역 화면에서 사용자 문의와 AI 답변이 함께 조회되도록 저장·조회 흐름 정리
* GitHub Issue 연동 과정에서 사용자 문의와 시스템 응답이 중복 전달되는 문제를 확인하고 전송 데이터 구조 개선

### DB 연동 및 운영 데이터 구성

챗봇이 단순 생성형 답변이 아니라 실제 게임 운영 데이터를 기반으로 응답할 수 있도록 PostgreSQL 기반 운영 DB를 설계하고 챗봇 응답 흐름과 연결했습니다.

* 회원, 게임 계정, 문의, 답변, 결제, 환불, 아이템 지급, 가챠 로그 간 데이터 관계 설계 및 정리
* 로그인한 사용자의 `user_id`, `account_id` 기준으로 본인 계정 데이터만 조회되도록 DB 조회 흐름 구성
* 실제 문의 데이터(`qa_ticket`)를 기반으로 결제·환불·아이템 지급·가챠 로그 데이터 생성 및 적재
* 결제·환불·아이템 미지급 문의에서 DB 조회 결과가 답변 근거로 활용되도록 데이터 흐름 연결
* 문의 접수, 답변 저장, 문의 내역 조회까지 이어지는 챗봇 데이터 저장 구조 정리

### Redis Cache 연동

반복 문의와 FAQ 문의 처리 비용을 줄이기 위해 Redis 기반 캐시 구조를 챗봇 검색 흐름에 연결했습니다.

* Redis 환경변수 설정 및 Redis Insight를 활용한 연결 환경 구성
* FAQ/RAG 검색 결과에 대한 Cache Hit / Miss 로그 확인 구조 적용
* 동일한 FAQ/RAG 검색 요청에서 검색 결과가 Redis에 저장되고 재사용되는 흐름 확인
* 반복 검색 비용과 응답 지연을 줄이기 위한 캐시 구조 정리
* 로컬 환경과 배포 환경의 Redis 연결 방식을 정리하고 팀원들과 공유

## 주요 성과

* 챗봇 문의 접수부터 답변 생성, 최종 응답 저장, 문의 내역 조회까지 이어지는 백엔드 흐름을 정리했습니다.
* 실제 게임 운영 데이터를 기반으로 결제, 환불, 아이템 지급, 가챠 로그를 구성하여 DB 기반 응답 근거를 마련했습니다.
* Redis Cache를 연결하여 반복 FAQ/RAG 검색 요청에서 검색 결과를 재사용할 수 있는 구조를 확인했습니다.
* 답변 저장 실패, `pending` 상태 유지, GitHub Issue 중복 전송 등 운영 중 발생할 수 있는 백엔드 이슈를 분석하고 개선했습니다.

## 데이터 구성

GameOps는 실제 고객지원 흐름을 반영하기 위해 문서 데이터와 운영 로그 데이터를 함께 사용했습니다.

### 문서 데이터

* FAQ
* 공지사항
* 이벤트 안내
* 정책 문서
* 커뮤니티 문의 데이터

문서 데이터는 RAG 검색에 활용되며, 사용자의 FAQ성 문의나 정책 관련 문의에 대한 답변 근거로 사용됩니다.

### 운영 DB 데이터

* 회원 정보
* 게임 계정 정보
* 문의 티켓
* 답변 초안
* 최종 응답
* 결제 로그
* 환불 로그
* 아이템 지급 로그
* 가챠 로그

운영 DB 데이터는 결제, 환불, 아이템 미지급, 가챠 관련 문의에서 사용자 계정 기준으로 조회되며, 챗봇 답변의 근거로 활용됩니다.

## 챗봇 처리 흐름

1. 사용자가 챗봇 화면에서 문의 카테고리를 선택합니다.
2. 사용자가 자연어로 문의 내용을 입력합니다.
3. FastAPI 백엔드가 문의 내용과 계정 정보를 수신합니다.
4. LangGraph 워크플로우가 카테고리에 맞는 에이전트를 실행합니다.
5. FAQ성 문의는 RAG 검색을 수행합니다.
6. 결제/환불/아이템 문의는 운영 DB를 조회합니다.
7. 답변 초안과 근거 데이터를 저장합니다.
8. 최종 응답을 생성하고 사용자에게 반환합니다.
9. 문의 내역 화면에서 이전 문의와 답변을 확인할 수 있습니다.

## 프로젝트를 통해 배운 점

이번 프로젝트를 통해 단순히 LLM으로 답변을 생성하는 것보다, 실제 서비스에서는 데이터 구조, 저장 흐름, 캐시, 응답 근거, 예외 상황 처리까지 함께 설계해야 한다는 점을 배웠습니다.

특히 챗봇 백엔드는 프론트엔드, 에이전트 워크플로우, 운영 DB, Redis Cache가 모두 연결되는 지점이기 때문에 각 계층의 데이터 흐름을 명확히 이해하는 것이 중요했습니다.
